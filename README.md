# 隱形浮水印實驗室

產生一把金鑰，蓋在你的作品上——肉眼看不出任何差別。然後驗給自己看、**試著用別人的金鑰偽造**、把圖摧殘一輪看它什麼時候會死。

每一步的中間產物都畫出來，沒有黑箱。**所有運算都在你的瀏覽器裡，圖片和金鑰都不會離開你的電腦。**

→ **[打開實驗室](https://yazelin.github.io/invisible-watermark-lab/)**

## 跟 LINE 對話製造機的關係

這個實驗室是從 [LINE 對話製造機](https://yazelin.github.io/line-chat-maker/) 長出來的——那個工具會在匯出的圖與影片上烙隱形標記，任何人都能驗出「這是合成的」。同一套場紋，換一個問題就是這一頁。

|  | LINE 對話製造機 | 這個 repo |
|---|---|---|
| 回答的問題 | 這張圖是不是這個工具做的 | 這張圖是不是**我**蓋的 |
| 圖樣哪裡來 | 固定的公開函式，8×8 節點 | 金鑰算出來的，16×16 節點 |
| 誰能驗 | 任何人（這正是目的） | 只有握有金鑰的人 |
| 判定 | 只看 z（門檻 7） | z > 6 **且** 峰值旁瓣比 > 6.5 |

**「為什麼那邊只看一個數字就夠？」我原本的答案是錯的。**以為製造機沒有金鑰、就沒有「別人的金鑰來撞」這種攻擊。實測（`node test/cross-lcm.mjs`）：這個 repo 用隨機金鑰蓋出來的圖，**60 張裡有 16～25 張被製造機判成「它做的」**（z 最高 9.4，門檻 7）。兩張隨機 ±1 圖樣總會有一部分格子同號，位移搜尋又會挑出最巧的對齊方式。

峰值旁瓣比分得開：製造機自己蓋的最低 7.1，這個 repo 蓋的最高 4.4。**正確的說法是「沒人去撞它」，不是「不可能誤判」。**

## 先搞清楚你要哪一種浮水印

| 題目 | 需求 | 代表 |
|---|---|---|
| **洩漏溯源** | 圖裡要載得動 ID，才知道是誰外流的 | [invisible-watermark](https://github.com/ShieldMnt/invisible-watermark)（dwtDct）、RivaGAN |
| **歸屬證明** | 只要回答「這是不是我的」，一個位元就夠 | **本專案** |

因為只需要一個位元，我們可以把全部的工程餘裕拿去換抗破壞性：平鋪、暴力搜尋、只看整體相關性。溯源型要精準到每個位元的位置，所以對裁切、縮放特別脆弱。

要防專業的、有心的移除，兩種都不夠。開源工具防的是順手盜用，不是防偽。

## 演算法

1. **金鑰 → 指紋**：`IWL2-XXXXX-…` 這段字串餵給確定性的 PRNG（xmur3 ×4 + sfc32），得到 16×16 個 ±1
2. **指紋 → 平滑場**：每 16 像素一個節點，格內位置過 smoothstep 再雙線性內插
3. **蓋章**：`藍 = 藍 + 2 × 場值`，近白近黑振幅減半，加 4×4 有序抖動再取整
4. **驗證**：每 16×16 格算 `藍 −(紅+綠)/2` 平均 → 減四鄰做高通 → 3σ 截尾 → 與指紋逐格相乘相加 → 標準化成 t → 取所有候選的最大值當 z，再算它比旁瓣突出多少（PSR）
5. **還原**：反解每個像素的原始藍值。實測 99% 以上逐像素完全相同，殘差最多 1/255（來自 0 與 255 的夾邊）

## 判定要同時過兩關

兩種假陽性的破口剛好相反，只看其中一個都會被另一種騙過去：

| | z（峰值強度） | PSR（峰值突出度） |
|---|---|---|
| 正向 | 43.7 | 13.7 |
| 裁一半 | 19.8 | 12.5 |
| 裁到 30% | 11.1 | 9.6 |
| **乾淨的圖** | 1.4（低） | **10.1（高）** |
| **別人的金鑰** | **13.2（高）** | 4.4（低） |

乾淨圖的分數分布很窄，所以 PSR 會衝高；別人的金鑰則相反，z 會跟著嵌入強度一起放大（你蓋得越用力，別人隨便一把金鑰撞出來的最高分也越高），但峰值並不突出。

所以判定是 `z > 6` **而且** `PSR > 6.5`。實測真陽性 40/40、假陽性 0/80，最接近門檻的距離 3.5（`node test/calibrate.mjs`）。

## 為什麼金鑰不是你的 logo

第一版真的是讓人上傳 logo 當金鑰，量出兩個補不掉的問題：

- **公開的東西不能當金鑰。** logo 通常是公開的，任何人拿得到就能蓋出你的浮水印。
- **自然圖片是低頻的**，但這一條沒有我原本寫的那麼致命。偵測端第一步就是高通，logo 縮成指紋後相鄰格子高度相關，高通把它殺掉一截——但**白化補得回大半**。2026-08-13 在同一張圖上重量（頁面附錄可以自己跑）：白化前 21.8、白化後 25.8、金鑰字串 26.4，裁 75% 三種都還活著。舊版寫「正向只有一半（25.0 對 43.7）、裁一半就驗不出來」是**拿兩張不同的圖比出來的，不成立**，已更正。**放棄 logo 靠的是第一條理由，不是這一條。**

隨機 ±1 沒有這兩個問題：相鄰獨立、每格用滿振幅。這也是 1997 年那篇奠基論文用偽隨機載波的原因之一。

logo 保留在鑰圖上當**標籤**——一資料夾長得一樣的 QR 你分不出哪張是哪張。它對演算法沒有任何貢獻，頁面上有寫清楚。

## 實際怎麼用

前六步是為了讓你看懂它怎麼運作。真正要用的時候是第七步：**作品流出去了，你拿回一張圖、配上當初存的鑰圖，問它「這是不是我的」。**

兩邊都不需要是同一次操作產生的——圖可以是別人傳給你的，金鑰可以是半年前下載的那張鑰圖（拖進去會自動從 PNG 的 iTXt 讀出來；只剩截圖的話用手機掃 QR 或照著明文抄）。

## 鑰圖

金鑰是資料，但存成一張圖：一串字放在記事本裡會不見，一張圖在相簿裡活得久。secret 在圖裡存三份，任何一份活著就救得回來：

- **PNG iTXt 中繼資料** — 主要路徑，重新上傳原檔直接讀
- **QR 碼** — 中繼資料被平台洗掉、或只剩一張截圖時，用手機掃
- **明文** — QR 也掃不到時，用眼睛抄

代價是「長得像照片的鑰匙會被當照片對待」，所以警告是**烙在像素裡**的，不是寫在頁面上：說明沒人看，但圖會跟著圖跑。

## 兩件量出來的、對自己不利的事

**指紋空間曾經只有 2³²。**金鑰是 100 bit，指紋是 256 格，但舊的 `rngFrom` 從一個 32 bit 雜湊連續吐四個數字去啟動 sfc32——看起來 128 bit，其實全由那 32 bit 決定。實測 30 萬把金鑰撞出 9～12 組完全相同的指紋（2³² 的期望值 10.5）。改成四次獨立雜湊後，同樣 30 萬把碰撞 0 組。新金鑰發 `IWL2-`，舊的 `IWL1-` 保留原路徑，以前蓋過的圖照樣驗得出來。`node test/keyspace.mjs`

**拿到一張蓋過的圖就能估出場紋，不需要金鑰、也不需要很多張。**原本文件寫「蒐集夠多張取平均才可能反推」，講輕了：一張就夠。攻擊者知道演算法，就能做跟偵測器一樣的事（高通、按 16 為週期折疊累加、取正負號），估中約 70% 的節點。拿去驗**另一張**同金鑰的圖會檢出（z 30–58），等於他有一把能用的金鑰；但拿去抹除只減掉一半（z 44→25，仍檢出）。這是平鋪式浮水印的結構性弱點——平鋪正是它抗裁切的原因。`node test/estimate-attack.mjs`

**「能裁掉多少」不是一個百分比，是尺寸的函數。**存活矩陣的斷點（剩 75%~60%）是 900×620 量的。同一種內容放大到 3600×2480，裁到剩 10% 還驗得出來；縮到 600×414 就幾乎裁不得。真正決定的是「剩下的格子數 × 每格的訊噪比」。連帶解掉另一條：高細節圖不是不能用，是要夠大。`node test/crop-vs-size.mjs`

## 誠實的界限

- **開源，所以拔得掉。** 防的是順手盜用，不是防偽。
- **金鑰外流就全毀。** 拿到它的人可以在任何圖上蓋出你的浮水印。這是唯一的信任根。
- **金鑰弄丟就證明不了。** 沒有伺服器、沒有備份、沒有「忘記密碼」。
- **同一把金鑰蓋很多張圖，理論上可以被反推**（平均攻擊）。真的在意就一件作品一把金鑰。
- **高細節、高雜訊的圖蓋不上去。** 密集紋理的測試圖連原圖都驗不出來（z=6.1）——不是被摧殘弄死的，是 ±2 的訊號蓋不過那張圖本身的雜訊底。
- **裁切比想像中脆弱。** 裁掉一半只有大面積淺色那張活，平滑漸層與實拍照片都死。關鍵是剩餘格數**加上**雜訊底夠低。
- **旋轉會殺死它。** 沒有搜尋角度，明確的已知限制。
- **剩下的區域太小就驗不出來。** 決定命運的是裁切，不是縮放：純裁切的斷點在留下 75% 到 60% 之間，而縮放幾乎不影響（縮到 25% 照樣驗得出來）。**反直覺的是，裁完再縮一半反而比只裁還耐用**——裁到 60% 單獨會死，裁到 60% 再縮一半卻活，因為縮小再放大等於過了一次低通濾波，把畫面的高頻雜訊壓掉、留下平滑的場紋，訊噪比反而變好。
- **未檢出不等於沒被盜。**

## 站在誰的肩膀上

這是 **spread spectrum watermarking**（擴頻浮水印），奠基論文是 Cox、Kilian、Leighton、Shamoon 1997 年發表於 IEEE Transactions on Image Processing 的 *Secure Spread Spectrum Watermarking for Multimedia*。他們埋在 DCT 係數，我們埋在空間域的藍色通道。

其他每一塊也都是既有技術：相關偵測與 t 統計量是訊號偵測理論的教科書內容；峰值突出度是雷達與相關濾波器的標準判準；利用人眼對藍色空間解析度低是感知模型浮水印的常見手法；平鋪加暴力搜尋做同步是對抗裁切的標準做法；有序抖動是印刷業的老技術。

| 專案 | 做法 | 跟這裡的差別 |
|---|---|---|
| [invisible-watermark](https://github.com/ShieldMnt/invisible-watermark) | Python，dwtDct／dwtDctSvd／RivaGAN | 載得動 ID，可溯源；抗裁切與縮放較弱 |
| [hiddenmark](https://github.com/hvuhsg/hiddenmark) | 瀏覽器端，傅立葉頻域環狀調變 | 方向最接近，頻域天生較抗縮放旋轉，實作複雜 |
| [watermark-js-plus](https://github.com/zhensherlock/watermark-js-plus) | 瀏覽器端，可見＋盲浮水印 | 功能最全，目標是保護網頁與文件 |

這裡自己的只有工程取捨與實測：±2 的振幅、16 像素節點、近白減半、抖動、雙門檻判定，以及那些做壞的版本被淘汰的過程。承認站在別人肩膀上，反而讓實測數據更可信。

## 檔案

```
index.html      工具 + 教學，一頁到底
pure.js         純邏輯：金鑰→指紋、嵌入、還原、偵測（node 可直接測，頁面用同一份）
field.js        瀏覽器端：指紋 → 平滑場 → 蓋章，附視覺化中間產物
detect.js       尺度搜尋與存活測試的摧殘手法
keyimage.js     鑰圖：QR + 明文 + iTXt 中繼資料 + 烙在像素裡的警告
app.js          頁面互動
vendor/         qrcode-generator.js（MIT, Kazuhiko Arase）
test/
  pure.test.mjs   純邏輯 16 項，含四條負控制
  calibrate.mjs   量 null 分布、定門檻(Z_MIN / PSR_MIN 的出處)
  survive-matrix.mjs  在四種代表性圖片上重量存活矩陣(ATTACKS 預期值的出處)
  e2e.mjs         真瀏覽器：產金鑰 → 蓋章 → 驗證 → 偽造 → 還原 → 存活矩陣
```

```bash
node test/pure.test.mjs     # 幾秒
node test/calibrate.mjs 60  # 約一分鐘
node test/e2e.mjs           # 約三分鐘，需要 google-chrome
```

**負控制不能省**：沒蓋過的圖必須驗不出來，別人的金鑰也必須驗不出來。做偵測類功能只量「抓得到」是不夠的，不然做出來的不是偵測器，是一個永遠說是的按鈕。
